# v0.2 实施计划：整理成记录

本文是 v0.2 的实施依据和进度记录，用法与 [plan-v0.1.md](plan-v0.1.md) 相同：任务完成后在第 6 节清单勾选并写一行备注；真机验证证据记入 [platform-matrix.md](platform-matrix.md)。

依据：[product-spec.md](product-spec.md) §4（v0.2 范围）、[schema.md](schema.md) §1.2/§1.3/§2.5/§2.6/§3/§4.3/§4.4、[decisions.md](decisions.md) D-05 至 D-11、D-16。

## 0. 背景与约束

- v0.1 的 M6 真机验收、T1 HealthKit 试验、T2 重签验证在真机可用时穿插执行，不阻塞 v0.2 开发（2026-09-27 记录）。
- v0.2 里程碑排序原则：**不依赖真机的先做**。模型配置、整理管线、日视图都可以在模拟器/单元测试里开发；HealthKit 读取的真机验证放最后。
- 遵守既有工程约定：迁移只追加不改旧迁移；改数据结构先改 schema.md；代码生成用 `dart run build_runner build --force-jit`。

## 1. 目标与完成标准

v0.2 做一件事：**消息被整理成饮食、睡眠、心情、不适、运动等记录，按日期查看、可修正；读取健康数据作补充；每日回顾只问缺的。**

完成标准 = A-08 至 A-14、A-23 至 A-25、A-30 至 A-32 在真机通过（见 product-spec §7）。

## 2. 技术要点

| 事项 | 方案 |
|---|---|
| 模型协议 | 自实现 HTTP 客户端，两种协议：`openai_compatible`（OpenAI / DeepSeek / Ollama / 自定义）与 `anthropic`。不引第三方 LLM SDK，减少依赖漂移 |
| API key 存储 | iOS Keychain（数据库只存 `keychain_ref`，schema §4.3）。候选包 flutter_secure_storage，真机小样验证后定 |
| 整理输出格式 | 模型返回 JSON（记录数组，每条含类型、TimeValue、data、来源片段），应用端严格校验后才进入提交流程；解析失败整批标 `failed`，不写半条记录 |
| 时间归属 | TimeValue 结构在应用层实现（schema §1.2）；"昨天/今天"由模型结合 `sent_at`/`sent_tz` 解析，凌晨歧义按 D-06 记前一天并标 `date_ambiguous` |
| 整理串行 | 单一整理队列（schema §3.1a），批次内逐项提交，快照校验按 D-05 |
| HealthKit | 沿用 health 13.x（T1 已装包）。**候选包差异（2026-09-27 V2-M4 确认）：** health 插件不支持 HKAnchoredObjectQuery，拿不到"已删除样本"和锚点。改为时间窗重读（上次同步前推 2 天）+ UUID 幂等去重；缺席不判定删除（符合 D-11）；**苹果健康中删除样本的同步删除（A-31 删除部分）待原生 MethodChannel 实现**，`health_anchors` 表留给它。活动能量没有统计查询，按来源优先级（Watch > iPhone > 其他）取单一来源求和，口径差异按 A-31 原则记录 |
| 文件预览 | open_filex 4.x，2026-09-27 真机验证通过：临时副本带原文件名和后缀交给系统预览（按哈希命名的无后缀文件系统认不出类型）|

## 3. 里程碑

按顺序交付，每步结束时应用可运行、`flutter test` 全绿：

- **V2-M0 数据层：** 建 v0.2 全部新表（`health_samples`、`health_daily`、`health_anchors`、`organize_runs`、`organize_run_items`、`model_calls`、`records`、`record_revisions`、`record_sources`、`model_configs`、`review_prompts`），迁移 schemaVersion 1→2；TimeValue 与 field_meta 的应用层模型；记录、整理批次、模型配置等仓库；单元测试覆盖：记录版本递增、来源链接、默认显示值排序（D-07）。
- **V2-M1 模型配置：** 设置页新增"模型"入口：预设（OpenAI / Claude / DeepSeek / 自定义兼容 / Ollama）→ 填 base_url、key、模型名 → 测试连接（写入 capabilities 与 data_boundary）→ 设默认。key 入 Keychain。模型调用记录页（每次调用发了什么，D-16）。
- **V2-M2 整理管线：** 整理队列与批次执行器：输入快照 → 组 prompt（消息 + 图片按能力）→ 调模型 → 解析校验 → 按 D-05 逐项提交（stale/protected/needs_manual 规则、retry_count ≤2）；触发器接入："记好了"、无输入 180s 预整理、每日回顾；无模型/失败时消息显示"待整理"。对应 A-08、A-09、A-10、A-23、A-24、A-30。
- **V2-M3 日视图与修正：** 日历/日期切换页，显示当天记录、设备数据与缺口；记录详情可点开来源消息；修正记录（字段级 `edited`，保留版本历史，A-25 的保护规则在提交侧已由 M2 实现）；对话流"已记到 X月X日"提示与歧义确认。**导出/恢复扩展到 v0.2 新表**（记录、版本、来源、整理批次、健康数据、回顾记账；`model_configs` 按 schema §4.3 不进备份），恢复后记录仍在。
- **V2-M4 健康数据：** HealthKit 读取睡眠、步数、体能训练、活动能量（授权文案、anchored query、按 D-11 合并睡眠、health_daily 聚合覆盖写入）；设备值进入默认显示值计算（schema §3.7）；模拟器/单测先行，真机授权与固定样本集验证等真机（A-12、A-13、A-31）。
- **V2-M5 每日回顾只问缺的：** 缺口检测（schema §3.5 表）、`review_prompts` 记账、当天不重复、最多 3 问、承认"没有"（A-14、A-32）；回顾通知点开进入带提问的对话流。
- **V2-M6 真机验收：** A-08 至 A-14、A-23 至 A-25、A-30 至 A-32 逐条执行，证据入 platform-matrix。可与 v0.1 的 M6 合并为同一次真机会话。

## 4. 交付检查

- 没有配置模型时一切录入功能可用，消息显示"待整理"（A-10）；
- 只配置本地模型且不可达时，不发生任何云端请求（A-11，data_boundary 检查在发送前）;
- 用户修改过的字段永不被整理覆盖（A-25）；
- 整理进行中修改输入不串版本（A-24）。

## 5. 风险与注意

- **模型输出不可控：** JSON 解析必须容错但不容错到编造——缺字段丢弃该条并记入批次 error，不猜默认值；`quality_score`、`mood.score` 只在用户明确给分时才有值（schema §3.5）。
- **UIScene 教训延续：** 每个里程碑用不挂调试器的方式验证启动。
- **Keychain 候选包：** flutter_secure_storage 若与免费签名冲突（keychain access group），退回 iOS 原生 MethodChannel 实现。
- **每次真机会话前先清 v0.1 欠账：** M6/T1/T2 优先。
