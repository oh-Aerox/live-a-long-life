# 用户需求

本文记录产品要满足的用户需求。怎么实现写在 [decisions.md](decisions.md)，页面与验收场景见 [product-spec.md](product-spec.md)。编号保持稳定，供其他文档和代码引用，空号不补。

## 产品定位

| # | 需求 |
|---|---|
| R-01 | 个人健康记录应用，积累的原始数据用于以后的健康风险分析和健康状况预测 |
| R-02 | 首先由开发者本人作为第一试用人，之后考虑给其他人使用 |
| R-37 | 产品定位是基于历史饮食、运动、睡眠、心情、压力等生活数据，结合疾病与体检数据做分析；针对单次就医或体检数据的解读分析不在本产品考虑范围内 |

## 日常记录

| # | 需求 |
|---|---|
| R-04 | 应用每天主动发起询问：三餐、入睡和起床时间、心情、身体不适、运动等 |
| R-05 | 用户也可以随时主动记录 |
| R-06 | 录入入口是简单的通知页面或对话页面 |
| R-07 | 支持一次录入多张图片、连续多段输入 |
| R-08 | 不设会话边界；"一段时间无输入"不算作用户已经结束或确认 |
| R-09 | 原始输入立即保存，整理可以稍后完成 |
| R-10 | 能从输入文字中提取时间，并把内容记录到对应日期。例如第二天补记昨天的内容，以用户说的时间为准，记录时间可以是当前时间 |
| R-11 | 每日回顾的时间由用户在设置中选择 |

## 病历与检查资料

| # | 需求 |
|---|---|
| R-12 | 能接收图片、PDF 等形式的病历和检查结果，并保存 |
| R-13 | 就医、体检数据由用户主动发起录入 |
| R-14 | 上传文件时检测重复：已上传过的文件再次上传时要给出提示 |
| R-32 | 针对长期积累、占用手机空间的病历及检查报告图片、PDF，提供原件清理入口，用于释放手机空间，保留提取出的历史医疗数据 |
| R-34 | 医疗记录描述过去发生的事实，正常使用无需修改；康复不改写或删除既往病史。原件清理不修改这些数据 |

## 用户资料

| # | 需求 |
|---|---|
| R-15 | 使用时收集用户基本资料，比如年龄、性别、运动爱好 |

## 设备健康数据

| # | 需求 |
|---|---|
| R-16 | 只读取手机上的健康数据，不对接任何手表品牌 |
| R-17 | 读取四项：睡眠、步数、体能训练、活动能量 |
| R-18 | 手机健康数据只作为补充，用于减少用户输入；缺少的数据通过对话获得 |
| R-19 | 用户主动录入的数据权重最高 |

## 平台与设备分工

| # | 需求 |
|---|---|
| R-20 | 支持 iPhone 和安卓 |
| R-21 | 完整实现 iPhone 和 Mac 两端；安卓和 Windows 的主要功能要确认可以适配，并明确记录哪些已实现、哪些待实现 |
| R-22 | 手机是数据录入的主力，电脑是数据分析的主力 |
| R-23 | 只用手机作为数据录入入口 |
| R-24 | 手机和电脑处于同一个 WiFi 时自动同步 |

## 存储与备份

| # | 需求 |
|---|---|
| R-25 | 数据保存在本地 |
| R-26 | 可选同步到用户指定的云服务做备份，比如 iCloud 或其他云（规划中，尚未实现） |

## 模型

| # | 需求 |
|---|---|
| R-27 | 应用内可以添加模型；用本地模型还是云端模型由用户决定：配置了本地模型就走本地，配置了云端模型就走云端 |
| R-28 | 预先对接好 OpenAI、Claude、DeepSeek 等模型的 API，用户只需填写 key 和 base URL |

## 分析与建议

| # | 需求 |
|---|---|
| R-35 | 周报除总结外，应根据个人数据给出下周在饮食、运动、睡眠等方面的建议；比如本周有就医时给出特别注意事项 |
| R-36 | 从就医、体检数据中区分长期身体状况与临时疾病：感冒发烧等临时疾病只影响近期在饮食、睡眠、运动上的建议；结石、囊肿、糖尿病、肩周炎、结节、过敏等不会消失甚至会发展的状况应列入长期建议 |
| R-38 | 提供主动咨询模型的入口，用户可以临时向模型提问获取建议 |

## 暂不做

| # | 需求 |
|---|---|
| R-29 | 暂不接入飞书、Telegram 等机器人录入入口 |
