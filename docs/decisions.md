## D-01 框架采用 Flutter

- **理由：** 一套代码覆盖 iOS、Android、macOS、Windows，满足 R-20、R-21。手机端和桌面端可以共用数据层与同步代码。
- **注意：** 相机、通知、后台任务、健康数据仍然需要各平台单独适配，并逐项在 [platform-matrix.md](platform-matrix.md) 里验证，不能凭"框架支持"就宣称已经适配。
- **替代方案：** React Native（桌面端要另选方案）；各平台原生开发（工作量翻倍）。

## D-02 本地存储

- 结构化数据存 SQLite，每条记录有稳定 ID 和版本号，修改历史单独保存。
- 照片、PDF 等附件按 SHA-256 命名存为独立文件，数据库里只保存引用。
- 每个设备上的数据都是一份副本，但**只有手机上的是可编辑的正式记录**（见 D-12）。
- **替代方案：** 纯 JSONL 或 Markdown 文件（便于人工阅读，但纠错、去重、查询都更难）；完整事件溯源（复杂度高，不能自动消除冲突，不值得）。

## D-03 数据分三层

| 层 | 内容 | 能否被覆盖 |
|---|---|---|
| 原始层 | 用户发的消息、附件内容及设备健康样本 | 模型不能覆盖。消息纠错保留历史；医疗附件可清理手机文件副本，但身份、索引和历史医疗记录保留（D-22） |
| 整理层 | 从原始层提取出的结构化记录（饮食、睡眠、症状等） | 可以产生新版本，旧版本保留在修改历史里 |
| 分析层 | 周报、趋势、就诊时间线、修正建议 | 可以重新生成；始终标明依据的数据截止点 |

整理层的每条记录都必须能追溯到它来自哪些原始消息或设备样本。模型更新、重新整理，都不能改变原始层。

## D-04 核对状态

| 状态 | 含义 | 什么时候进入 |
|---|---|---|
| `unreviewed` 未核对 | 模型提取出来，用户还没有明确确认 | 整理批次生成时 |
| `confirmed` 已确认 | 用户明确确认过 | 用户点了确认，或在修正建议上点了接受 |
| `edited` 用户已修改 | 用户亲自改过 | 用户编辑时 |

- 日常记录不强制逐条确认，界面上也不因此增加点击；
- 检查单的关键字段（项目、数值、单位、参考范围、检查日期）必须确认后，才能作为"事实"参与分析；
- 分析可以使用未核对的数据，但输出里要标明。

## D-05 消息流 + 整理批次

- **原始层是一条按时间排列的消息流。** 用户和应用发出的每条消息都按先后顺序保存，每条消息发送后立即持久化。
- **不设会话边界**（R-08）。"一段时间无输入"只能触发后台预整理，不代表结束，也不代表确认。
- **整理批次**是对一组"尚未整理"或"需要重新整理"的消息做的一次模型处理，产出若干条记录的新版本。触发时机：
  1. 用户点"记好了"；
  2. 短暂无输入后的后台预整理；
  3. 每日回顾；
  4. 用户在某条记录上点"重新整理"。
- 新消息和已有记录相关时（比如"米饭只吃了一半"），重新整理时生成该记录的新版本，而不是新建一条记录。
- **并发规则：** 只比较消息序号不够，因为旧消息可能被修改、附件可能被删除、记录可能被用户改过。批次开始时记下三类输入快照：
  1. 每条输入消息的修订号（`messages.revision_no`）和删除状态；
  2. 每个输入附件的版本与当前设备文件可用状态（`attachment_copies`）；
  3. 每条目标记录当时的版本号（`base_version`）。
- **提交时在一个事务里逐项校验**，每条记录单独提交、单独记结果，不因为一条失败而整批作废：

  | 校验结果 | 处理 |
  |---|---|
  | 输入和目标版本都没变 | 写入新版本 |
  | 输入消息被修改、目标数据作废，或出现新的相关消息 | 这一项作废，消息重新排队，由新批次基于新输入处理 |
  | 附件本地文件暂不可用 | 等待原件取回后处理；不删除已有整理结果。正在提取的文件不进入空间清理任务 |
  | 目标记录已被其他批次更新（仍是模型结果） | 这一项作废，重新排队 |
  | 目标记录的某些字段是 `confirmed` / `edited` | 这些字段不覆盖；如果新结果不同，生成一条修正建议给用户（D-12），建议绑定本次提交后的目标版本；其余字段照常写入。这一项到此完成，不为同一保护冲突重新调用模型 |
  | 同一输入因输入或目标过时连续重排 2 次 | 标为"需要手动处理"，不再自动重排，避免无限循环 |

- **新建记录的 ID 在批次开始处理时就生成**，提交前已有稳定身份；每一项的提交把记录版本、来源链接、项状态和消息状态写在同一个事务里，中途退出后重试时跳过已完成的项（schema §3.1a）。
- **整理批次串行写入：** 同一用户只有一个整理写入队列，不同触发合并排队，同一输入不会被两个批次并行处理、重复建记录；消息的整理状态在所有相关项落定后再汇总（schema §3.1a）。
- **一条消息可以关联多条记录。** 比如"午饭后到现在一直胃胀"，同时关联到午饭记录和一条症状记录。
- 字段级的来源和核对状态见 D-07、schema §1.3。

## D-06 时间语义

对应 R-10。区分事件的自然日期和界面上的显示分组。

- **发生时间和记录时间分开保存。** 记录时间是消息的发送时间，由系统自动记录；发生时间从内容里提取，以用户的说法为准。
- **发生时间的精度：** 精确时刻 / 大约时刻 / 时段（早上、中午等）/ 只到日期 / 未知。"大概一点"要保存为"大约 01:00"，不能加工成精确值。
- **时间来源：** 用户明确说的 / 根据发送时间推断的 / 设备记录的。没有提到时间时，按发送时间推断并标为"推断"。
- **时区：** 有具体时刻时保存 UTC 时刻和事发时的 IANA 时区；只有日期或时段时，只保存本地日期（`local_date`），**不编造 UTC 时刻**。
- **自然日期：** "今天""昨天""9 月 25 日"一律按发送者所在时区的自然日（00:00 起算）理解。明确写出的日期永远不被改写。
- **凌晨的"今天"有歧义时保留待核对：** 凌晨发送、说的是"今天"，但内容明显指发送时刻之后才会发生的时段（比如 01:00 说"今天晚饭吃了面"），按自然日理解会得到一个还没发生的时间。这种情况下候选日期取前一天，标为未核对，并在对话流里提示"已记到 9月25日，对吗？"。能按自然日得到合理结果时（比如 01:30 说"今天一点才睡着"），直接按自然日。
- **显示分组（可选）：** 设置里的"日视图从几点开始"只影响按日视图怎么分组显示（比如 04:00 前的记录显示在前一天），不修改任何记录的日期。默认 00:00，即不偏移。
- **睡眠：** 知道醒来时间时，归到醒来那天，界面上显示为"9/25 晚 — 9/26 晨"；只知道"昨晚睡得不好"而不知道醒来时间时，按原话的自然日期保存，不推算醒来日期。

## D-07 数据采用顺序

对应 R-19。同一事项、**同一字段**有多个来源时，按下面的顺序决定默认显示哪个值：

1. 用户修改过或确认过的值（`edited` / `confirmed`）；
2. 从用户原话中提取、尚未核对的值；
3. 设备数据；
4. 模型推断（比如根据消息时间推断出的日期）。

- 只在同一字段内比较："一点上床"和设备记录的"入睡时间"是不同字段；"睡得不好"和设备记录的睡眠时长可以同时存在。
- 设备数据刷新后，不能覆盖用户已表达的值。
- 所有候选值都保存，默认显示值是按规则算出来的，不单独存储。
- **来源和核对状态记到字段级：** 一条记录里可能 `bedtime` 是用户修改过的、`quality` 是模型提取的、`duration` 来自设备。比较在字段上进行，不在整条记录上进行。
- **同级比较规则：** 同一字段、同一级别有多个候选值时，取最新的那个（用户值按消息的发送时间，设备值按样本更新时间），其余保留为候选，界面上可以查看。
- **同一天同类事件不合并：** 一天里两次运动、两次加餐是两条记录，不能因为类型相同就当作同一事项比较字段。只有模型或用户明确把它们关联到同一条记录时才比较。

## D-08 每日回顾：缺口检测

回顾前按日期检查各项数据的情况，只问缺的。缺口按**字段**判断，而不是按"有没有这类记录"判断。

**每个检查项的状态：**

| 状态 | 含义 | 是否再问 |
|---|---|---|
| 已记录 | 有用户记录或设备数据 | 按下表 |
| 明确没有 | 用户说了"没吃早饭""今天没运动""没有不舒服" | 不问。这是有效回答，不是缺失 |
| 待整理 | 有相关消息但还没整理（没有模型或整理失败） | 不问具体内容，避免重复 |
| 已跳过 | 这次回顾问过，用户跳过了 | 当天不再问 |
| 缺失 | 以上都不是 | 问 |

**字段级缺口举例：** 有睡眠记录但只有入睡时间、没有醒来时间，可以问醒来时间；有午饭记录但只有照片、没有说吃了多少，不追问（饮食的必填字段只有"吃了"这件事本身）。每类记录哪些字段参与缺口检测，在 schema §3.5 中标注。

**按数据来源决定问法：**

| 数据项 | 已有用户记录 | 只有设备数据 | 都没有 |
|---|---|---|---|
| 睡眠 | 不问 | 只问感受："记录到昨晚睡了约 6.5 小时，感觉怎么样？" | 问时间和感受 |
| 三餐 | 不问 | — | 只问缺的那一顿 |
| 运动 | 不问 | 确认一下："记录到步行 40 分钟，还有别的运动吗？" | 简单问一句 |
| 心情 | 不问 | — | 问 |
| 身体不适 | 不问 | — | 问（用户明确说"没有"时记为"明确无不适"） |

上表是按类别的概括，与字段级缺口判断冲突时以字段级为准：已有用户睡眠记录但缺醒来时间，仍然可以问醒来时间。

- **每次回顾一般 1 到 3 个问题，最多 3 个。** 缺口多于 3 个时按优先级取前 3 个：身体不适 > 睡眠 > 三餐 > 心情 > 运动。缺口问题不满 3 个时可以补一个用户资料问题（见 D-18）；资料问题计入总数，一次回顾包括资料问题在内最多 3 个（A-32）；
- 用户可以跳过任何问题，跳过的项记为"已跳过"，不积压成待办；
- 每次回顾问了什么、每个问题的结果（已回答 / 已跳过 / 没有回应），保存在 `review_prompts` 表中（schema §4.4），用于当天不重复提问；
- **没配置模型时：** 已整理的记录和设备数据照常参与检测；有未整理消息的日期按"待整理"处理，不追问细节；如果当天既没有记录也没有消息，就问通用问题，比如"今天吃饭、睡觉、身体都还好吗？想补记什么都可以。"

## D-09 回顾问题用规则模板生成

- 问题来自固定模板，按缺口检测的结果选择和填充，不需要调用模型。
- **理由：** 没有模型也能用；问法稳定、可测试；问法固定也便于审查和控制，减少提问方式对回答的影响。
- 让模型把问题改写得更自然（问题内容仍由规则决定）作为可选项，尚未实现。

## D-10 去重与幂等

对应 R-14。

- **文件精确去重：** 导入时计算 SHA-256。如果已存在相同文件，弹出提示："这份文件已于 {日期} 上传过"，提供三个选项：查看已有 / 仍然添加 / 取消。选择"仍然添加"时，不重复存储文件，只新增一条引用。
- **手机副本已清理的文件再次上传：** 按保留的 SHA-256 匹配，提示"此报告已录入，手机原件已清理"，可补回本地文件或取消。补回文件后沿用原附件 ID 和来源定位，不自动新建医疗记录、不覆盖已核对数据（D-22）。
- **医疗文件内容级重复：** 同一份病历截图一次、拍照两次，SHA-256 各不相同；相册每次导出也会重新压缩，同一张照片字节都不同，精确去重拦不住。病例夹添加文件时，**导入前**先在本机识别文字（结果按 SHA 缓存，提取时复用），与已有医疗文件逐个附件比较：文字二字组包含度 ≥ 0.8 **且** 两位以上数字（日期、时间、编号、数值）多重集包含度 ≥ 0.9 才提示"可能已经上传过"，提供查看已有 / 仍然添加 / 取消（取消不留孤立附件）。只看文字会把同一医院的定期复查检验单（项目名、参考范围相同）误判为重复，数字把它们分开。实测参考：同一病历重拍约 0.95/0.94，截图与照片约 0.84/1.00，病历与检验单约 0.14/0.41。只是提示，附件身份仍按 SHA-256。不采用图片感知哈希：重拍（角度、光线不同）的距离约 47/256，与不同照片（100～150）分不够开。
- **同一检查的重复提取：** 提取检验结果时，同一检查日期已有包含相同项目的检验记录，提示"可能重复"（可能是同一份报告拍了两次），两份都保留，核对时由用户留意。
- **清理确认说明导出副本：** 清理只删应用内部存储的原件，用户导出（文稿/exports）里的副本不动；选中的文件在导出里有副本时，确认框写明份数和位置（文件 App → 我的 iPhone → 长命百岁 → exports），避免以为空间已全部释放。
- **删除医疗文件：** 医疗文件详情提供删除（重复上传的清理出口），文件、提取记录、从它建议但未核对的状况一起标记删除；已确认的状况档案保留（R-34），原始照片/PDF 仍在消息流（D-27）。
- **消息幂等：** 每条消息在客户端生成 UUID，重复写入相同 UUID 时直接忽略。
- **同步幂等：** 按"来源设备 + 数据代次 + 变更序号"传输，接收端重复收到同一变更时忽略；同一实体收到比本地更旧的版本时也忽略（D-13）。

## D-11 苹果健康只读

- 入库的只有四项：睡眠分析、步数、体能训练、活动能量（R-17）。每项的用途在权限申请前向用户说明。咨询时实时读取的其他类型不入库，见 D-44。
- 不回写苹果健康，避免影响其他应用使用的数据。
- iOS 不会告诉应用"用户拒绝了读取"，未授权和"确实没有数据"看起来是一样的。所以读不到数据时，界面显示"暂未读取到记录，可手动补充"，不能显示成"今天没有运动"，也不能判定"你拒绝了权限"。
- 步数、活动能量按天聚合保存；睡眠样本和体能训练记录按条保存，用 HealthKit 样本 UUID 去重。
- **增量读取：** 睡眠和体能训练用 anchored query 读取，同时拿到新增和已删除的样本；锚点持久化保存。苹果健康里删掉的样本，本地对应标为已删除，不再参与显示和分析。首次读取或锚点失效时，重新读取最近 30 天；30 天之前已导入的样本标为"未复核"，不当作已与苹果健康核对过。重读时没有返回的样本，不能仅凭缺席判定已被删除——读不到和被删除无法区分，仍按"暂未读取到"处理。
- **睡眠汇总规则：**
  - 苹果健康里"在床上"和各睡眠阶段（核心、深度、REM、清醒）的样本会重叠，多个来源（手表、手机、第三方应用）也会重叠，不能直接相加；
  - 同一晚的样本合并成一段睡眠：按时间排序，相邻间隔不超过 1 小时的归为同一段（试验参数，用真实数据验证后调整）；各段的起止和清醒间隔保留，不只存一个总数；
  - **睡眠时长** = 各睡眠阶段（不含清醒、不含"在床上"）去掉重叠后的总时长；没有阶段数据、只有"在床上"时，显示"在床 X 小时，睡眠时长未知"，不把在床时长写入睡眠时长字段；
  - **入睡 / 醒来时间** = 这一段里第一个和最后一个睡眠阶段样本的起止时间；
  - 多个来源同时有阶段数据时，本应用默认优先 Apple Watch，其次 iPhone，再次其他应用。这是本应用自己的合并口径：苹果健康允许用户另行调整来源优先级，所以不以"与苹果健康显示一致"为承诺，验收以固定样本集的计算正确性为准（A-31、P-10）；在设置中调整这个顺序尚未实现。
- **按天聚合的口径：** 步数、活动能量用 HealthKit 的统计查询，按**当时设备时区**的自然日 00:00—24:00 聚合，保存聚合使用的时区和起止时刻。跨时区旅行当天以聚合时的时区为准，不回溯重算。
- **时区的含义：** 健康样本上保存的时区是读取时设备的时区，不一定是事件发生时的时区，字段上要标明"推断"（schema §2.5）。

## D-12 写入者分工

| 数据 | 谁能新建 | 谁能修改 |
|---|---|---|
| 消息、附件、记录、用户资料 | 手机 | 手机 |
| 设备健康样本 | 手机（从 HealthKit 读取） | 不可修改 |
| 分析结果、修正建议 | Mac；手机的整理批次遇到用户已确认或修改的字段时，也会生成修正建议（D-05） | 重新生成 |

- 只有一台手机作为编辑入口。安卓可以适配，不等于允许 iPhone 和安卓同时编辑同一份档案。换手机通过导出与恢复进行（D-34），专门的迁移流程尚未设计。
- Mac 的修正建议回传到手机，用户接受后才写成记录的新版本。

## D-13 局域网同步

- **配对：** Mac 显示二维码，内容包括一次性令牌、Mac 证书指纹和地址。手机扫码后双方交换证书，之后只与配对过的设备通信。
- **传输：** 使用 TLS，双方都用配对时固定下来的自签证书做认证。同一 WiFi 只是尝试连接的条件，不代表可信。
- **发现：** 使用系统 Bonjour / mDNS：Mac 广播 `llal-<设备 ID>`，TXT 带局域网地址；手机按记录的地址连不上时，按设备 ID 查找并更新地址。发现只提供地址，连接仍走配对时建立的加密认证，冒名广播连不上；发现失败退回原地址与手动重新配对。
- **手机 → Mac：** 按变更序号增量传输。附件按哈希传输，Mac 校验通过并写入磁盘后返回确认，手机收到确认才标记为已同步。传输中断后可以续传。
- **Mac → 手机：** 回传分析结果和修正建议，同样按序号增量传输。
- **变更日志：** 手机业务数据的新增、纠错与作废进入 `change_log`。D-22 的手机文件清理只改变设备副本状态，不产生医疗记录删除事件，不要求 Mac 删除原件。文件可用性单独通告，不能触发医疗数据版本变化。
- **确认游标只推进到连续确认的位置：** Mac 可能先确认了 15、再确认 12，中间的 13、14 还没到。手机上的"已同步到"只能推进到从头开始连续确认的最大序号，不能取已确认序号的最大值。
- **附件依赖：** 引用附件的变更，要等附件本身确认后才算完成。Mac 可以先保存记录，但在附件到齐前把它标为"附件缺失"。
- **来源和代次：** 每条变更带来源设备 ID 和数据代次（generation）。代次是随机生成的唯一标识，不是递增数字：同一份备份恢复两次会得到两个不同的代次，不会和旧的确认状态碰撞。完整恢复是用户明确执行的操作：恢复后手机开启新代次，Mac 按新代次以手机当前状态重建手机数据的副本（D-34），不做跨代次的版本号大小比较。Mac 自己生成的分析结果不在重建范围内。
- **不合并待发送变更：** 每条变更按序号依次发送、依次确认，即使同一实体有多条未发送的变更。"只发最新一条"的优化需要先定义一次确认覆盖哪些旧序号，否则连续游标会永远停在被跳过的序号上，因此不做。
- **文件传输与清理：** 发送中的手机文件暂不清理，完成后再执行清理；手机本地清理不取消 Mac 已接收的档案。手机不会因普通后台同步自动下载已经主动清理的文件，只有用户明确选择取回时才下载。
- **Mac 端也有变更序号：** 分析结果和修正建议从 Mac 回传时，用 Mac 自己的变更日志和游标，规则相同。
- **同步时机：** 打开应用时、完成一次录入后、iOS 给出后台执行机会时，以及用户点"立即同步"时。界面显示最后一次成功同步的时间和待传数量。
- 不承诺手机锁屏时一回家就立即同步。
- 同步完成后手机默认保留原件；用户可以主动清理手机副本（D-22）。Mac 原件继续保存，供查看和备份。

## D-14 分析结果的数据截止点

- 每份分析结果都记录生成时依据的手机端变更序号（数据截止点）。
- **按分析范围判断过期：** 只看"引用过的记录"不够，因为新增的记录、被删除的记录、新读到的健康数据都没被引用过，却会改变结论。每份分析结果记录它的**依赖范围**：日期区间、涉及的数据类型（饮食、睡眠、健康样本等）。截止点之后，只要这个范围内有任何新增、修改、删除，或健康数据更新，就标为"需要更新：之后有新的记录或修正"。
- 引用过的记录后来有了新版本，属于上面的情况之一，照样标为需要更新。手机本地原件清理不改变历史事实，不令已有分析过期；引用处只更新原件是否可在当前设备打开。

## D-15 备份

- 由 Mac 端生成带版本的完整备份：用 SQLite 在线备份接口生成数据库快照，再加上附件文件，打包后加密。备份目前固定存放在电脑的"文稿/长命百岁备份"目录（Windows 为"文档"）；让用户选择备份位置、备份到 iCloud Drive 等云服务尚未实现（规划中，对应 R-26）。
- 备份文件是加密的整包，不是正在使用的数据库文件本身，所以不存在"云盘同步导致 SQLite 损坏"的问题。
- 在开始积累真实数据的早期，完成一次"从备份恢复到新环境"的演练，结果记录在平台矩阵里。
- API key 不进入备份。
- **按清单生成，保证数据库和附件对得上：**
  1. 先保护本次归档所需的文件不被回收，再做数据库快照，记下快照对应的变更序号（截止点）；
  2. 根据快照生成**文件清单**：Mac 已归档附件的哈希、大小；未归档原件单独列为缺失，不能把仅有提取数据标成原件完整备份；
  3. 清单登记后保持对应 Mac 文件可读直到备份结束；备份任务失败或应用重启后，释放遗留的文件保护，不让保护无限期滞留；手机副本清理不影响 Mac 文件，也不减少后续备份中的原件；
  4. 打包加密，写到临时文件名；
  5. 解密校验：清单里每个文件都在、哈希一致、数据库能打开；
  6. 校验通过后才改成正式文件名，成为可用的备份。校验失败就删除临时文件，保留上一个可用备份。
- **恢复流程：** 选择备份 → 输入备份密码（或从 Keychain 取密钥）→ 校验清单 → 恢复数据库和附件 → 列出缺失或损坏的文件（不因为个别文件缺失而整体失败）→ 开启新的数据代次（D-13）。目前 Mac 上提供的是恢复演练（解密到临时目录并校验，不动当前库）；从备份完整恢复尚未实现。
- **备份密钥：** 首次开启备份时由用户设置备份密码，派生密钥保存在 Mac 的 Keychain。换电脑或 Keychain 丢失时，只能用密码恢复，所以设置时要提醒用户妥善保存密码。
- **备份保留策略：** 旧备份按设置轮换（尚未实现）。清理手机文件不触发备份轮换、清除或重建，Mac 与备份中的原件继续保留。
- **三种操作分开：** 手机空间清理只释放当前手机文件；取回原件只补回一个文件；备份恢复用于丢失数据、重装或迁移。不能把"康复"或"清理原件"当作恢复/重置整个数据库的理由。

## D-16 模型接入

- **按协议适配：**
  - OpenAI 兼容协议覆盖 OpenAI、DeepSeek、Kimi、智谱 GLM（D-33）及其他兼容服务，以及 Ollama、LM Studio 等本地服务；
  - Anthropic 协议用于 Claude。
- **配置流程：** 选择服务预设 → 填写 key → 选择模型 → 测试连接。自定义 base URL 放在高级设置里。
- **能力标注：** 每个模型标明支持文本、图片、PDF 中的哪几项。测试连接时分别用示例内容验证。不支持图片的模型，图片保持"待整理"状态，不能报告为保存失败。
- **只配一个默认模型。** 不同任务分别配置模型作为以后的高级功能，尚未实现。
- **数据边界：** 每个模型配置标明数据会到哪里——本机、局域网（比如 Mac 上的 Ollama），还是云端。当配置的本地或局域网模型不可用时，任务排队等待，**绝不自动改走云端**。
- **透明度：** 每次调用都记录发送了哪些消息和附件（记 ID，不记 key），以及实际发送的用户侧正文（`model_calls.request_text`，系统提示词是代码常量不重复存），用户可以在调用记录页展开查看、复制。
- **key 的存放：** 只存在系统安全存储中（iOS Keychain / Android Keystore / macOS Keychain），不进入数据库、同步、导出或备份，每台设备单独配置。
- **Mac 端也用同一套模型接口：** Mac 上的分析同样通过应用的模型配置调用模型，遵守同样的数据边界和调用记录，不能绕开。

## D-17 平台矩阵的状态

六种状态：未开始、开发中、已实现待验证、验证通过、受阻、本期不做。另外用"不适用"表示某个平台没有这项能力。"验证通过"必须附上验证证据，详见 [platform-matrix.md](platform-matrix.md)。

## D-18 用户资料逐步收集

- 首次使用只收集必要的内容：时区（自动检测后确认）、每日回顾时间、是否授权读取健康数据。
- 年龄、性别、运动爱好等资料在首次使用时可以直接填写，也可以跳过。跳过的项，之后在每日回顾中每次最多追加问一项。
- 每项资料都说明用途，都可以选"不愿透露"。
- 年龄保存为出生年月，而不是年龄数字；性别区分"生理性别"（影响检查参考范围）和可选的"性别认同"。

## D-19 免费签名下的开发与试用

- 保持固定的 bundle ID 和签名团队，避免频繁新建 App ID，因为免费账号在这方面有数量限制。
- 提供一键重签安装脚本（`scripts/resign-install.sh`）。用户每 7 天连一次 Mac，运行一条命令即可。
- 应用内在签名到期前提醒；到期前先完成一次同步或备份。
- 验证覆盖安装后数据保留（验收场景 A-07）。卸载重装不作为常规续签步骤。
- 免费账号不支持远程推送，本项目只使用本地通知，不受影响。

## D-20 电脑端分析的形态

外部 agent 直接读取数据快照会绕开 D-16 的数据边界和调用记录，所以分析默认由应用自己发起。

- **默认路径：** 分析由 Mac 应用发起，通过应用的模型配置调用模型（D-16），遵守数据边界、记录每次调用发送了什么；在 Mac 应用内生成和查看周报，结果再回传手机。
- **命令行入口（尚未实现）：** Mac 应用提供命令行触发分析，只返回任务状态和结果 ID，不在终端输出报告正文——这样 skill 作为适配器调用时，不会借终端输出读到健康内容；结果在 Mac 应用内或回传手机后查看。
- **外部 agent 的位置（尚未实现）：** Claude Code / Codex skill 可以作为两种角色之一：
  1. **适配器：** skill 只调用 Mac 应用的分析命令，由应用负责取数据、调模型、写结果。skill 本身不读取健康数据；
  2. **用户明确选择的入口：** 用户在设置里主动开启"允许外部 agent 读取数据快照"，开启时说明"数据会发送给该 agent 使用的模型服务，不受应用数据边界限制"。每次读取都记录到调用记录里。默认关闭。
- **触发：** 手动触发（"生成本周周报"）。每周固定时间自动触发尚未实现，实现时只使用数据边界允许的模型。
- **失败处理：** 模型不可用时任务排队，不改用其他模型；生成失败时保留上一份结果，显示"本周周报生成失败：{原因}"，可以重试；不输出半成品。
- **结果格式：** 无论哪种路径，结果都按分析结果的格式写入（schema §6.1），必须带数据截止点和依赖范围，再同步到手机。

以后给其他人使用时，面向国内还是海外，会影响安卓生态（Health Connect 的可用性）、合规要求（比如《个人信息保护法》中关于敏感个人信息的规定），以及默认模型服务的选择。R-02 所说的后期阶段开始前需要确定。

## D-22 医疗原件的手机空间管理

对应 R-32、R-34。主要处理长期积累的病历、检查报告图片和 PDF，目的是释放手机空间。产品按钮命名为"清理手机原件，保留记录"。

### 保留与清理的对象

- 保留提取出的诊断、指标、就诊及检查日期、用药记录等历史事实，以及核对状态、来源 ID、页码定位、文件指纹和医疗记录之间的关联。
- 只移除所选原件在当前手机上的大文件副本及可再生预览缓存，不改动原始事实、已核对字段、记录版本或分析结论。
- Mac 和备份中的已有文件不联动删除：它们作为档案保留，手机作为按需查看端。
- 康复、后续复查和新的检查结果作为新的带日期记录追加。"曾经得过某病"仍是历史事实，不因为康复而改写。识别错误、误录等纠错仍可保留历史进行，不属于空间清理。

### 最小使用流程

1. 上传文件 → 提取 → 核对 → 保存历史数据；之后在医疗文件详情或"设置 → 医疗文件空间"中选择原件清理。
2. 页面列出本地文件大小、提取/核对状态、其他设备的原件保存情况（最后确认时间）。默认批量选择已完成提取和核对的报告；正在导入、提取或传输的文件本次不清理。
3. 提示"将释放约 X MB，历史记录保留；Mac 原件不受影响"。没有已确认的其他副本时，说明清理后可能无法再打开原件；未核对内容仍标为未核对。用户可以取消、先归档，或明确选择仅保留已提取数据，不强制购买云服务。
4. 实际文件移除成功后更新手机副本状态与释放空间；记录仍能查看和参与符合核对规则的分析。文件暂被占用时显示"等待清理"，不能提前宣称空间已释放。

### 按需查看与重复上传

- 手机已清理、Mac 有文件：显示"手机原件已清理，可从 Mac 取回"；用户点开并选择取回后，沿用现有同步通道传文件并校验哈希。Mac 不可达时仍可查看提取数据。
- 没有可用副本：显示"原件当前不可用，历史记录保留"，允许用户以后重新提供同一文件；不能假装可恢复。
- 再次提供同一文件，按 SHA-256 补回同一个附件，恢复来源跳转，不重新创建相同的病历/指标。不提供"不保留指纹"的额外分支。
- 多条消息/记录引用同一文件时，手机文件只清理一次、占用只计算一次，所有引用保留。普通同步不会把清理过的文件自动下载回来。

### 不扩展的范围

- 不把空间清理扩展为文字消息清除、字段级级联删除、分析正文脱敏、跨设备彻底抹除或清除所有旧备份。
- 普通消息误发/录入纠错保持独立入口；对既往医疗记录不提供因康复而重写事实的自动行为。
- 删除整个档案等需求如以后提出，单独设计，不作为原件清理的前置工作。

## D-23 医疗提取管线：本地 OCR 优先

对应检查单/病历导入（product-spec §10）。

- **分流：** PDF 先探测有无文字层。有文字层直接抽取文本（零识别误差，不走 OCR）；扫描件 PDF 逐页渲染成图后与照片同路径。
- **本地 OCR：** iOS / macOS 用系统 Vision 框架（免费、离线、中文印刷体质量好），通过 platform channel 调用，双端复用；Android 用 ML Kit。输出文字和每段文字的 bounding box 坐标。较新系统的文档级识别（表格结构）作为可选增强、老系统降级为普通文字识别，尚未实现。
- **发送前本地页筛选：** 体检报告册含大量与健康无关的页（封面、机构介绍、导读/目录、健康宣教、指标科普附录、温馨提示），发给模型前按页打分筛除。两个信号：①锚点关键词——保留锚点如"检验项目/结果/单位/参考范围""所见/提示/结论/印象""总检/汇总/异常/建议"，丢弃锚点如"导读/目录/尊敬的/温馨提示/健康宣教/本中心简介"（与脱敏共用锚点基础设施）；②数值密度——"数字+单位+参考范围"模式的每页密度，高密度页必是数据页。注意：检查文字报告（超声/心电图的"所见/结论"）和总检结论是散文体但健康相关，必须保留；"异常指标解读"页可能混排用户本人异常值，默认保留。**默认筛选 + 用户可改，不静默丢弃**：导入界面每页缩略图带"已排除"标记，可点选恢复（复用 pages 页序 UI）。筛选只影响发送副本：原件与全部页的 OCR 文本本地完整保留，被排除页以后可补提取；locator 页码坐标不受影响。收益除省 token 外，还避免无关内容稀释模型注意力、降低抽取准确率。
- **结构化交给模型：** 项目、数值、单位、参考范围、检查日期的抽取由默认模型完成——把 OCR 文本（带行/区块索引）经页筛选和脱敏（D-24）后作**纯文本调用**发送，要求模型对每个字段返回其引用的行索引，应用再映射回 OCR 坐标写入 `lab_panel.locator`。这是 A-19"每个数值定位回原件页码或区域"的实现基础：多模态模型看图给不出可靠坐标，OCR 天然有。发送前先让用户预览和修改，见 D-28。
- **多模态看图仅作兜底**，且只能显式调用（D-24）。
- **理由：** 坐标溯源；隐私（原图默认不出设备）；成本（纯文本调用便宜）；无模型或未配模型时 OCR 文本照样保存，结构化可以之后补跑。
- **注意：** OCR 输出只是原始层的派生缓存，不算事实；结构化结果一律 `unreviewed`，识别与抽取错误由 D-04 逐项核对兜底。
- **替代方案：** 多模态模型直接看图（手写、复杂版式更强，但无坐标、图片出设备，保留为兜底路径）；纯规则结构化（各医院报告格式差异大，太脆，不采用）。

## D-24 提交模型前的隐私处理

遮蔽范围：**姓名、证件号和门诊卡号**（含就诊卡号、诊疗卡号、门诊号，占位符 `【卡号】`，容忍 OCR 把"门诊"读成"门1诊"）；**出生日期保留**。

- **文本路径（默认路径）的脱敏，三层，全部本地执行：**
  1. **锚点标签取邻值：** 按"姓名""身份证号/证件号""社保卡号/医保卡号"等标签词定位，把紧邻的值替换为占位符。利用单据版式而不是猜内容，命中率最高；用 OCR 坐标（同行或右邻区域）取值比按字符串顺序更稳。
  2. **身份证号校验位正则：** 18 位身份证按国标加权模 11 校验位匹配，近零误报；匹配前做易混字符归一化（O→0、l/I→1 等），防 OCR 误读漏网。
  3. **用户本人姓名全文替换：** 应用是单用户的，直接全文替换已知姓名，覆盖标签之外散落的姓名。
- **已知姓名的来源：** 资料里的"姓名（只用于发送前遮蔽）"，以及同一份文件里第一层标签旁识别出的姓名和敬称版式（"尊敬的××先生"、单独一行的"×× 女士"）。封皮、页眉上单独出现的姓名没有标签，靠这一步覆盖：收集后对整份文件每页全文替换，字间允许空白（封皮大字常加字距）。收集的值必须是 2～6 个汉字，泛称句子不收。
- **占位符替换（如 `【姓名】`、`【证件号】`）而不是直接删除**，文本结构不塌、坐标映射不断；维护"占位符 → 原文坐标"的本地映射。
- **脱敏只作用于出设备的发送副本。** 原件和未脱敏 OCR 文本始终只存本地；调用记录里记录本次遮蔽项数（D-16 透明度）。
- **明确保留不删：** 年龄、性别（参考范围与分析依赖，完整出生日期可降级为年龄）、检查日期（必要字段，日期格式先摘出，不被号码规则误伤）。
- **规则不承诺零泄漏：** 家属姓名、电话、住址等规则漏掉的内容，由发送前预览（D-28）让用户兜底。
- **图片路径（多模态识图）仅显式调用：** 图片永不隐式发给模型（整理与周报只发文本和 attachment_count，唯一发图的是测试连接的内置探测图）。医疗文件详情提供明确的"用模型识图"入口，调用前提示"建议先裁掉姓名、证件号区域"。应用内不做图片打码。
- **裁剪：** 用应用内框选（iOS 没有可供任意应用调用的系统裁剪界面），框外压暗、只发框内；裁剪图在内存里生成、长边不超过 2048 像素，**只用于本次发送、不落库**，存档原件始终完整；调用记录只记尺寸与裁剪区域。裁剪可跳过（有些报告姓名与指标混排裁不开），跳过裁剪发整页前再确认一次风险。默认模型的图片能力看测试连接写入的 capabilities，不支持时提示换模型、不发送也不记失败。识图结果与文字路径同样建成 lab_panel（全部 unreviewed），没有行号，定位为页码 + 裁剪区域。

## D-25 长期状况与临时疾病的区分

对应 R-36、R-37，是医疗提取与分析的口径。

- **两类医疗信息：**
  - **临时疾病：** 感冒、发烧、急性肠胃不适等预期会痊愈的。只影响近期（比如 30 天内）在饮食、睡眠、运动上的建议，不进长期档案，对长期建议几乎没有影响。
  - **长期状况：** 结石、囊肿、结节、糖尿病、肩周炎、过敏等不会消失、甚至会发展的。记入**长期状况档案**，长期参与分析和建议。
- **落地：** 记录类型 `condition`，字段含名称、确认来源（检查报告 / 就医 / 用户自述）、首次发现日期、最近复查日期、发展情况描述（schema §5.2a）。复查、康复追加新版本，不改写历史（R-34）；分类由模型建议、用户核对（D-04），未核对不作为分析事实。同一问题的识别与合并见 D-32、D-46，已痊愈的处理见 D-41。
- **分析输入：** 周报及咨询的输入包含长期状况档案 + 近期临时疾病，使建议有针对性（R-35）。
- **定位边界（R-37）：** 本产品做**纵向分析**——基于历史饮食、运动、睡眠、心情、压力等生活数据，结合疾病与体检数据看趋势和关联。**不做单次报告解读**：单份检查单的价值是提取核对入库后进入纵向趋势和长期档案，不提供"分析这一份报告"的独立功能。

## D-26 主动咨询入口

对应 R-38：临时需要问模型一些建议。

- **形态：** 独立的"咨询"页，用户输入问题发给默认模型，同一咨询会话内可多轮追问。模型按需查阅数据的方式见 D-43。
- **数据边界（D-16）：** 初始上下文是用户问题 + 最小上下文（年龄、性别等基本资料摘要、长期状况摘要）。每次发送了什么记入调用记录（`caller=userConsult`），可展开查看实际发送的正文（D-16）。医疗类只发已核对内容：未核对状况不发；报告只发已核对的诊断/结论、异常值、药名。
- **与录入的边界：** 咨询是问答不是录入——内容不进消息流、不参与整理、不生成记录。要把咨询中提到的事记下来，用户回消息流正常录入。咨询历史本地保存可回看。
- **提示词：** 内置健康助手定位——结合提供的个人上下文回答，不做诊断、不给用药方案，需要就医时明确建议就医（见 [prompts.md](prompts.md)）。

## D-27 病例夹、体检入口与检验项目索引

- **两个入口，一套实现：** "我的病例夹"（病历、检验/影像报告、处方、出院小结等）和"我的体检"（`doc_type = physical_exam`）是同一医疗文件列表的两个过滤视图。列表按检查日期/上传时间排列，可添加（拍照/相册/PDF）、查看、进入详情提取与核对。
- **导入仍写入消息流：** 原始层是消息流（D-05），病例夹只是视图 + 导入捷径。从病例夹添加文件时创建一条附件消息（走 D-10 去重提示），medical_documents.pages 引用该消息的附件——不为医疗文件另开一条原始数据通道。
- **检验项目冗余索引 `lab_results`（schema §5.3）：** 每个检验项目展开一行（item_key、数值、单位、参考范围、检查日期、核对状态、来源记录/文件），供按项目提取历史数值分析。定位是**派生索引而不是事实源**：
  - 随 lab_panel 记录版本在同一事务里重建，用户核对/纠错后索引自动跟上；
  - 不入变更日志、不同步、不进备份，各设备从已同步记录自行重建（可整表重算）——避免索引与记录双写不一致这类分布式问题。Mac 接收同步时按单条记录重建（记录与版本任一到达都触发），启动时整表重建；
  - 机构名等展示信息查询时联 medical_documents 取，不冗余进索引，防文件信息更新后索引过期；
  - 查询键 item_key 由项目名按本地规则归一化（D-32、D-36、D-38、D-39、D-42）；按标准编码（item_code，LOINC 映射）归并尚未实现，索引结构已预留。
- **替代方案（未采）：** 把 results 拆成独立业务表做事实源——查询同样方便，但记录版本机制（不可变修订、来源链接、核对状态）要整套复制一遍，双写一致性代价高；分析取数时实时展开 JSON——无冗余但每次全表扫描，趋势视图要的就是按项目索引。

## D-28 医疗提取先预览后发送；文字内容同等提取

- **先提取、再展示、最后发送：** 点"识别并预览"只在本机做文字识别、页筛选和脱敏，然后进入"发送前确认"页，逐行展示将要发给模型的全部文字（所见即所发），自动遮蔽的占位符高亮。用户确认里面没有个人信息后点"确认发送"才调用模型；从预览页返回什么都不发。
- **预览可改：** 任意一行可改写或整行删掉（规则漏掉的家属姓名、电话、住址等由用户兜底）；每页可切换发送/不发送（沿用 D-23 的页覆盖）。修改只作用于本次发送副本，原件与本地识别缓存不动；删掉的行不发送，模型引用这些行号时丢弃。调用记录的 `sent_summary` 写明发送页数、行数、自动遮蔽数与手动修改行数。
- **确认页修改随文件保存：** 每改一行立即存进 `medical_documents.line_edits`（键为附件 + 附件内页号 + 行下标，调整页序后仍对得上；带修改时的原文，识别结果变了就不套用），下次打开确认页自动恢复并提示恢复了几处；右上角"全部还原"清空。提交失败或离开后不用重删。多选：长按一行（或点"多选"）进入，点选勾选，再长按另一行把两行之间整段选上，每页可"全选本页"，批量"删掉选中的行"或"恢复选中的行"。
- **文字内容同等提取：** 门诊病历的主诉/诊断/处理意见、超声等报告的所见/提示/结论，与检验数值一样提取，按栏目存入 `lab_panel.findings`（schema §5.2），逐段核对（D-04）、可定位回原件。只有文字没有数值的文件（如彩超报告）不显示为"未提取"、不丢弃。状况建议（D-25）另建。
- **识别纠错：** OCR 常有形近字（会明→会阴）、断行、表格列被拆散交错。模型按医学常识和上下文修正明显错误、把拆散的内容重组并归入正确栏目，**每处修正写进 `ocr_fixes` 供用户核对**；拿不准不改；数值、单位、参考范围、日期、剂量里的数字不许按常识修正，只允许明确的字符混淆（O→0 等）。修正前的原文留在 locator，可对照原件。理由：照原文逐字抄写会保留识别错误，对用户没有用。
- **处方药品：** 病历、处方、医嘱里开具的药品单独提取为 `medications`（名称、规格、单次用量、用法、频次、疗程、数量），逐条核对。
- **页多行多时分批：** 一份十几页、几百行的体检报告一次发送会超时，单次输出上限也装不下几百个项目。发送行数超过约 90 行时按页分批（整页不拆），最多两批同时在途，每批失败重试一次；仍失败的批次点名页码，其余批次照常保存（未核对，可重新提取补上），全部失败才不建记录。每批各记一条调用记录。
- **文件类型以用户选择为准：** 提取回填文件级信息时，文件类型只在还是"其他"（病例夹新加、未分类）时由模型判断补上；从"我的体检"加的文件保持体检报告，不被覆盖。
- **一份文件一条提取记录：** 重新提取在原记录上追加版本（历史保留），不另建，避免同一份报告的数值在索引和分析里出现两遍。
- **超时：** 提取调用单独放宽到 180 秒，其他调用为 60 秒。

## D-29 Mac 端只读医疗视图

电脑端是分析数据的主力，同步来的医疗数据在 Mac 上也要能看。

## D-32 同一问题只算一次，当前状况取最新

体检报告前面的汇总把问题列一遍、后面的明细再写一遍，分批提取时两处落在不同批里，会各自成为记录；多份不同年份的体检都写了同一问题（如肾囊肿从 5 毫米长到 8 毫米），看当前状况时应该只看最新的。常见情形：汇总与明细重复的检验值（同一转氨酶项目，汇总写"低"、明细写带缩写的全名和"↓"）、同一问题两种写法的状况（"颈椎轻度骨质增生"与"颈（3）-（6）椎体缘轻度骨质增生"）、汇总里解释原因和给建议的句子被当成异常描述。

- **同一项、同一问题怎么认（本地规则，`app/lib/data/same_item.dart`）：** 检验项目名去掉括号里的英文缩写与检测方法、中文名后斜杠跟的缩写（"体重指数/BMI"）再比；中文说明（"尿沉渣"）保留，免得不同标本混在一起。问题名称去掉序号、检查名前缀（"腹部超声提示："）、括号内容、程度与左右等修饰（轻度、中度、多发、双侧）再比：核心相同，或较短的核心不少于 3 个字、按顺序出现在较长的里、且最后两个字相同（结石、增生、囊肿），就算同一个问题。
- **提取时合并（同一份文件）：** 分批结果合并后，同项目同数值的检验结果只留一条，留信息更全的（有参考范围、异常标记，值里没混单位）；同一问题的状况建议只建一条，留名称更具体的。这份文件或同一检查日期的文件（重复上传）已经建过的不再建。其他日期报告里的同一问题照样建，每份报告各有一条、各自关联原文件，历史不改写（R-34）。
- **检验项目索引：** item_key 按上面的规则归一化，同一记录里同项目同数值只建一行，趋势图上同一天不出现两个点。索引启动时整表重建，归一规则改动后下次打开就按新键。
- **看当前状况取最新：** 人体图、长期状况档案、咨询上下文、周报输入里，同一问题的各条状况归成一组，按最新那份报告算，首次发现取最早日期，既往写法列在"此前"里；检验项目每项只看最近一次，最近一次正常就不再提示；后来的报告一直没再提到的，用能取到的最后一次。
- **人体图上的报告文字：** 一份文件在某个器官上已经有诊断（状况建议），这份文件的报告文字不再单列到这个器官（诊断是对所见的归纳）；同一份报告已据此下诊断的检验值（"尿酸高"的诊断与对应的尿酸数值）只列诊断。解释原因、给建议的句子（"……与肥胖有关""建议定期复查"）和写着"正常"的小句不算异常；检查名前缀不参与判断和归属（"耳鼻喉科提示：慢性鼻炎"只归鼻）。
- **已有记录：** 不自动改已有记录。人体图、档案页、咨询按上面的规则读，打开就生效；医疗文件详情页里汇总与明细重复的检验值仍在，想清掉可以对那份报告重新提取（在原记录上追加版本，按规则合并）。同一报告里的重复状况，档案页里归成一行显示。
- **同一指标的不同写法：** 白细胞分类的"比值 / 比例 / 百分比 / 百分数"归百分数，"计数 / 绝对值"归绝对值；去掉"（联）"（联合检测）、不带括号的检测方法（"……电发光"）、末尾的"测定 / 检测 / 定量 / 定性"（去掉后剩不到两个字的不去）、中文名后空格跟的英文缩写；外加一张保守的别名表（谷丙转氨酶→丙氨酸氨基转移酶等，只收同一指标同一标本的叫法，不收尿素氮 / 尿素这类口径不同的）。游离前列腺特异性抗原与前列腺特异性抗原、尿常规白细胞与血常规白细胞计数仍分开。
  - **比值换算：** 白细胞分类写成小数比值的（如 0.48，参考 0.5-0.7；没有单位、参考上限不超过 1），进检验索引时乘 100、单位记 %，与别的报告的百分数画在同一条趋势线上；原文写进参考说明（"50-70（原文为比值 0.48，参考 0.5-0.7）"），记录本身不改。
  - **仍认不出的：** 别名表之外的叫法、换了标本或口径的同名指标。规划中：提取时让模型给出标准项目名，本地规则兜底（同 D-31 的器官标签）。

## D-33 模型预设加 Kimi 与智谱 GLM

模型配置的"服务"下拉里可以直接选 Kimi 或 GLM。

- **两家都走 OpenAI 兼容协议**，不新增协议：Kimi 默认地址 `https://api.moonshot.cn/v1`（国内平台；国际平台的 key 要把地址改成 `https://api.moonshot.ai/v1`，key 只在签发它的平台可用），模型名提示 kimi-k3；智谱默认地址 `https://open.bigmodel.cn/api/paas/v4`（后面不再加 /v1），模型名提示 glm-5.3。Coding 套餐的专属地址不预设，用户可以手改。
- **调低思考：** 两家的新模型默认深度思考，kimi-k3 默认最高档。整理与提取是按原文抄写归类，用不上深度思考，还会拖慢（体检报告一批可能超过 180 秒提取超时）、占用 max_tokens。Kimi 预设请求带 `reasoning_effort: low`，智谱预设带 `thinking: {type: disabled}`；其他预设不带。
- 模型配置不同步、不导出、不进备份（D-15）。

## D-34 手机从导出恢复后，Mac 按新代次重建副本

手机从导出恢复后换了数据代次（D-13），Mac 需要以新代次重建这台手机的副本（schema §7.3）；手机也要在新代次里把恢复回来的数据重新发出，否则 Mac 只能拿到恢复之后新写的变更。

- **手机端：** 回填标记记"已回填的代次"，代次变了（恢复、换手机）启动时在新代次里把全部同步范围内的数据（含医疗文件）补一遍，已在本代次日志里的跳过。导出不带这个标记。回填时只有本机有文件的附件才带文件依赖：清理过或恢复缺件的附件本机传不出文件，带上会让同步卡在这一条（Mac 早收到过的文件照常记副本）。
- **Mac 端：** 收到新代次先拒收，记下"待重建"，首页提示"某手机从导出恢复过，需要重建副本"。用户点处理、确认后，**先自动备份一次，备份成功才**清掉副本里这台手机的数据，接收进度改到新代次、从第 1 条重新收；手机下次同步把现有数据全部重发。
- **只提供"以手机为准"：** 不做"保留 Mac 多出的"。恢复后手机的消息序号从导出时接着编，和 Mac 上导出之后才收到的消息撞号，按唯一键覆盖会把它们顶掉，承诺的"保留"做不到。需要找回时用重建前的那份备份。
- **保留的：** Mac 自己产生的行（修正建议、周报、调用记录、Mac 上的整理）、其他已配对设备的行、已收到的原件文件。按 `created_on_device` 区分，认不出的设备标识算这台手机的。检验索引重建后整表重算。

## D-35 用模型整理医疗文件的文字内容

本机识别后的诊断与检查文字基本准确，但分条机械：超声等报告把同一部位的描述和结论拆成两条（条目"甲状腺"：形态大小正常，回声均匀；条目"检查所见"：甲状腺未见异常），体检报告汇总和明细也会重复。

- **入口：** 医疗文件详情"用模型识图"下方有"用模型整理"，文字内容有两段以上才出现，确认后才发送。提取提示词仍"按栏目分条"，整理是事后可选的一步，调用失败不影响已提取的结果。
- **发送的数据：** 只发当前版本已提取的 findings（栏目 + 内容），它们来自脱敏后的文本；不发图片、行号和原始识别文本。caller 记 `phoneMedicalExtract`，调用记录可查。
- **合并规则：** 同一部位/同一检查的所见与结论合成一条，栏目写部位或检查名，内容按"所见：……\n结论：……"分行；意思相同的重复只留一条；病历栏目（主诉、诊断、处理意见、建议等）各自独立。原文不摘要不改写，数字不动。
- **应用侧防线：** 每段输入必须落进某一条输出（模型返回 `from`），漏了就整个不改；一条也没合并时不写新版本。合并条目的定位和识别修正取来源各条的并集，仍能逐处回原件。原样保留的条目保持核对状态，合并出来的回到未核对（D-04）。
- **可撤销：** 写成记录的新版本，旧版本在修改历史里；提示条上可以撤销（整理后又改过就不撤）。
- **下游：** 咨询摘要按栏目名（诊断/结论/提示/印象）挑要点，也认内容里带"结论："等标签的行（合并后的条目栏目是部位名）。人体图按内容里的异常句子归器官，不受影响。

## D-36 检验项目记录所属检查大项，尿、便检查的项目单独成项

体检报告按大标题分组（血常规、尿常规……）。不记大项时，尿常规的"白细胞""葡萄糖""胆红素""pH""比重"在指标趋势里看不出来自尿常规：尿"葡萄糖(GLU)"会与空腹血糖同键、画在同一条趋势；尿"白细胞(LEU)"不带"尿"字，人体图的"尿白细胞"规则用不上；"比重""尿胆原"与"尿比重""尿胆素原"会分成两项。

- **提取时记大项：** results 每项有 `panel_raw`，按报告大标题原文；提示词要求尿常规、便常规里的项目一定填，项目名照原文、不自己加"尿"。识图兜底同样。
- **查询键加标本：** 大项是尿、便检查的，键前加"尿/便"并统一写法（白细胞→尿白细胞，葡萄糖→尿糖，蛋白质→尿蛋白，比重/尿比重→尿比重，尿胆原/尿胆素原→尿胆原，pH 值→尿液酸碱度，潜血→隐血）；血液类大项和没有大项的不变。pH 不用"尿pH"作键：人体图的 Hp（幽门螺杆菌）规则不分大小写会误中。
- **认标本的例外：** "尿"后面跟"酸/素"的不算（尿酸、尿素是血液项目），前有"糖"或后跟"病"的也不算（大项"糖尿病检测"里的空腹血糖不能键成"尿空腹血糖"）。
- **镜检与干化学：** 镜检的有形成分（白细胞、红细胞、上皮细胞、管型、结晶）不论写"（高倍视野）""(HPF)"还是"（镜检）"，键统一为"尿白细胞（镜检）"这样；要在去英文括号之前认，否则"白细胞(HPF)"会和血白细胞同名。没有大项的镜检有形成分按尿算。干化学"白细胞(LEU)"测的就是白细胞酯酶，与"尿白细胞酯酶"同一项；镜检与干化学方法不同，仍分开。
- **展示：** 指标趋势按大项分组（见 D-42）；尿、便项目详情标题带大项。医疗文件详情的检验结果按大项分段，供核对；修改单项时可以改大项。大项不是 D-04 的关键字段，不影响核对状态。
- **人体图、咨询：** 尿、便项目按带标本的键归器官（尿白细胞→膀胱，尿蛋白、尿液酸碱度→肾）；咨询摘要的异常指标前带"尿常规"。
- **分批续表：** 长报告分批发送（整页不拆），后一批可能从续表开始、没有大标题。提示词要求按项目名称和缩写判断大项，判断不出（身高、血压）才留 null。不做"批首继承上一批的大项"的本地规则：批次并发发送，且新一页可能是另一张没标题的表。
- **补空缺：** 用模型补而不是重新提取（重新提取会让核对状态清零）。有检验项目没有大项时，详情页出现"用模型补大项"：按报告顺序发项目名称和已有的大项，靠前后已标的补空缺，不发数值；只填空的，核对状态不变；写成新版本，可撤销。
- **索引表：** `lab_results` 有 `panel_raw` 列（schema §5.3），启动时整表重建；Mac 同样。

## D-37 医疗文件的就诊标题，机构与检查日期可改

- **可改：** 医疗文件详情的医疗机构、检查日期、就诊标题都可以点开修改或补填。重新提取只在字段为空时填，不覆盖已有值（可能是用户改的）；代价是识别错的要手动改一次。
- **检查日期联动：** 改日期时，提取记录（lab_panel）和从这份文件建议出的身体状况一起写新版本改日，检验趋势随记录重建索引。
- **就诊标题：** 提取提示词的 `doc` 有 `visit_title`，模型按发送的（已脱敏）文字概括诊断或主诉、体检名称或检查名和部位，12 字内，不写医院、日期、人名；多批发送取第一个非空。不另调模型，随提取一次返回。病例列表与就诊时间线以标题为主标题，类型放在副行；没有标题的仍显示类型。
- **存储：** `medical_documents` 有 `visit_title` 列，随医疗文件同步、导出、备份。同步按列写入，手机与 Mac 需要使用同一数据库版本。

## D-38 检验项目名的互认标记不区分项目

化验单有的项目名前带"*"，表示地区间检验结果互认，对健康记录没有意义；同一项目有的报告带、有的不带，不处理会在指标趋势里分成两条。

- 项目名前后的"*""＊""★""☆""※""▲""△""●""◆"在查询键里去掉，带不带标记的归同一项；指标趋势、人体图、咨询摘要展示的项目名也去掉。
- 原文 `item_name_raw` 不改，医疗文件详情的核对列表仍按报告原样显示，方便对照原件。
- 不改提示词：标记去掉是本地规则，旧报告不用重新提取；检验项目索引启动时整表重建，键随之更新。

## D-39 血压拆成收缩压、舒张压；复测并入同一条趋势；红细胞压积统一成百分数

有的体检报告把血压写成一项"122/86"（值不是数字，画不出趋势，且和分开写的不是同一项），有的收缩压、舒张压分开写，还有"复测血压""收缩压（复测第1次）"（多为"-"）。

- **建索引时拆，记录不改：** `lab_results` 主键含 `part`；血压一项写的拆成收缩压、舒张压两行，参考范围、异常标记按斜杠拆（参考范围没分开的不套用，异常标记两项都带）。不改提示词、不要求重新提取（重新提取会让核对状态清零），医疗文件详情把两行合回一行"血压 122/86"，确认、修改、删除作用于这一条原文。
- **复测并入：** 键去掉"复测"，和首次测量画在同一条趋势，同一天数值不同就是两个点；同值的按同一份报告重复只留一行。
- **替代方案（未采）：** 复测单独成项、主趋势只取首次。
- **占位值：** "-""—""未测"等建索引行（报告核对里还能看到、能删），趋势与"最近一次"不取。
- **红细胞压积：** 有的报告写小数 0.45（单位 L/L 或不写），有的写 44.0%，同一条趋势会从 0.47 跳到 44。按白细胞分类的比值规则换算：单位为空、"-"或 L/L 且参考上限（没有时看数值）不超过 1 的乘 100，原文写进参考说明；"红细胞比积""血细胞比容"归同一项。
- **血小板压积：** 血小板压积、血小板比积、血小板比容（PCT）同一项；有的报告写小数 0.0022（参考 0.0011-0.0028），有的写百分数 0.25，都不带 %，按量级判断：参考上限（没有时看数值）小于 0.05 的乘 100（单位印错成 fL 的也有，单位只认 %）。平均血小板体积/血小板平均体积（MPV）、血小板容积分布宽度/血小板体积分布宽度（PDW）也归同一项。
- **同名归并：** 红细胞参数 MCH（平均红细胞血红蛋白含量/平均血红蛋白含量/平均血红蛋白量）、MCHC（平均红细胞血红蛋白浓度/平均血红蛋白浓度）、MCV（平均红细胞体积/红细胞平均体积）、RDW-CV 与 RDW-SD 的"-CV""-变异系数""变异系数"各种写法；含量与浓度不合。白细胞分类"相对值"即百分数（数值本身是百分数，不换算），"嗜酸细胞""嗜碱细胞"即嗜酸性、嗜碱性粒细胞。括号里的"（定量）""（定性）"和不带括号的一样去掉（甲胎蛋白（定量））。尿胆素原归尿胆原。

## D-40 首页入口与医疗文件核对页的组织

- **健康档案页：** 底栏"健康档案"是一页：病历与体检（病例夹、体检、长期状况、时间线）、指标与分析（人体图、趋势、周报、修正建议），每个入口旁标待核对、未提取、待处理的数量。底栏图标下有名称；"健康档案"图标上的角标只算待处理的修正建议（待核对的文件可能长期存在，做角标会一直挂着）。
- **设置分组：** 记录与提醒 / 模型 / 数据与同步 / 关于 / 开发者（运行日志）。"数据存储位置"的说明如实写明会与 Mac 同步、会调用模型，不写"没有任何网络上传"。
- **医疗文件核对页：** 顶部显示"已核对 x/y · 异常 n"，可筛选全部 / 未核对 / 异常；异常（有异常标记或超出参考范围，与人体图同一口径）的数值加粗标红。主按钮随状态变（未提取"识别并预览"，有未核对"全部确认（N 项）"），重新提取、用模型识图、整理文字、补大项收进"更多"，各带一句什么时候用。删除一条、全部确认一步生效，提示条上可以撤销（之后又改过就不撤）。

## D-41 已痊愈的长期状况作为既往病史，只作背景

已痊愈的长期状况如果和进行中的混在一起发给模型，模型可能仍按现有疾病给建议（结石已排出还提醒饮水）。

- **单列为既往病史：** 周报与咨询把已痊愈/解除的长期状况单列为 `past_conditions`，提示词说明"只作背景参考，不要当作现在的疾病"；结石、过敏这类会复发的对模型仍有参考价值。人体图不显示已痊愈的状况。
- **替代方案（未采）：** 已痊愈的完全不发。
- **其他规则：** 未核对的不进任何分析（D-04）；已痊愈的临时疾病不发；后来的报告又写到同一问题时按那条新的算，重新变成进行中（D-32）。
- **档案页标题：** "长期状况（参与分析；已痊愈的只作既往病史参考）""临时疾病（只影响近期建议；已痊愈的不再参与）"。

## D-42 指标趋势的分组归一，按项目认分组

报告的大项写法五花八门（"生化"与"生化检验"、"肿瘤"与"肿瘤标志物"、"过敏原IgE28项检测（回）"等），没标大项的项目（续页上的过敏原、血型、传染病筛查、血压等）会都落进"其他"，有的报告把心脏超声标成"测量"。

- **按大项关键词归一（`SameItem.panelGroup`）：** 过敏/变应原/IgE→过敏原检测，肿瘤→肿瘤标志物，生化→生化，肝功、肾功、血脂、血糖/糖尿病/糖化、甲状腺/甲功、凝血、幽门、肺功能、风湿、视力/色觉→眼科、血型、传染/感染/乙肝/术前→传染病筛查、一般/体格→一般检查；都不中的去"检查/检测/检验/测定"后缀。规则按关键词写，同类报告换个叫法也归到同一组。
- **按项目认分组（`SameItem.trendGroup`，先于大项）：** 血压、身高体重等→一般检查；左室、射血分数等→心脏超声；ABO/RH 血型→血型；乙肝、丙肝、梅毒（TRUST）、艾滋→传染病筛查；MTHFR→基因检测；常见食物、吸入过敏原（尘螨、花粉、皮屑、霉菌等）→过敏原检测。不管报告怎么标大项、标没标都归同一组。没有大项、键带"尿/便"标本的归尿常规/便常规（尿酸、尿素除外）。
- **组的顺序：** 常见顺序为血常规、尿常规、便常规、肝功能、肾功能、血脂、血糖，其余按名字，归不进任何组的为"其他"。
- **一个项目归哪组：** 按检查日期取最近一次能认出分组的，最近那份没标大项时不掉进"其他"。分组只影响趋势展示，记录不改。
- **同项不同名补充：** "血清肌酐""血清尿酸"等去"血清"前缀（去掉后不足两个字的不去，如血清铁）；括号里带全角破折号的缩写（"hs—CRP"）同样去掉。
- **认不出的：** 没标大项、又分不出尿还是血的项目（如"PH值""葡萄糖（阴性）"）仍在"其他"，由用户在详情里改所属大项或用模型补大项（D-36）。

## D-43 咨询采用 agent 形态：模型按需调用只读工具

- **形态：** 咨询页有"允许模型查阅我的记录"开关（设置键 `consult_allow_lookup`，默认开，记住上次的选择）。打开时模型拿到的初始上下文与 D-26 相同（基本资料 + 已核对状况档案 + 会话历史，另加今天日期），需要具体数据时自己调工具查、看结果再决定下一步，最多 6 轮，最后一轮禁止调用工具，逼模型作答。关掉时一问一答，只带初始上下文。
- **五个只读工具（`ConsultTools`）：** `get_records` 按日期范围查日常记录摘要；`get_device_data` 查已同步的苹果健康睡眠、步数、活动能量、体能训练；`list_lab_items` 列检验项目及最近一次数值；`get_lab_history` 查某项历次数值；`search_medical_documents` 查报告里的文字结论、异常指标和开药。日期范围单次最多 31 天、报告最多 15 份，防止一次把全部数据发出去。**医疗类一律只给已核对的内容（D-04）。** 工具不写库，咨询仍不进消息流、不生成记录。iPhone 上另有实时读取苹果健康的工具，见 D-44。
- **可查（D-26）：** 每一轮模型调用各写一条调用记录（caller 为 userConsult）：首轮 request_text 是初始上下文，之后是本轮发回的工具结果；返回内容记模型要调的工具和参数。问题下方的"发送了"后面列出查了什么（如"查阅：记录 10-20~10-26（12 条）、检验历史"血红蛋白"（1 项 5 次）"）。
- **协议：** `ModelClient.chatWithTools` 同时支持 OpenAI 兼容（tools / tool_calls / role=tool）和 Anthropic（tools / tool_use / tool_result）。模型的回复按协议原样回传：Anthropic 整个内容块数组（含 thinking 块），OpenAI 兼容带回 reasoning_content（Kimi 等思考型模型要求）。
- **兜底：** 第一轮带工具的请求被拒（HTTP 400/422，多半是模型或服务不支持工具，如部分 Ollama 模型）时自动改为一问一答，问题下方注明"模型不支持查阅，按原方式回答"。网络错误、认证错误照常报错。
- **替代方案（未采）：** 每次把近 N 天全部数据塞进上下文——简单，但发出的数据远多于回答需要的，且长期指标历史塞不下；模型可写的工具（直接记录、修改）——违背"写入必须经用户确认"（D-05），不做。

## D-44 咨询时实时读取苹果健康，不入库

除睡眠、运动、步数等入库的四类外（D-11），手机健康里的其他数据（心率、血氧等）不保存，咨询问到时实时读取再分析，例如"昨晚睡眠如何""这次运动心率如何"。

- **工具 `read_health_live`（`HealthLiveReader`）：** 一次读一个指标，时间精确到分钟、单次最多 31 天。可读：心脏（心率、静息心率、步行平均心率、HRV、心率过高/过低/不齐提醒、房颤负荷、心电图分类与平均心率）、呼吸与体征（血氧、呼吸频率、体温、睡眠手腕温度、血压、血糖）、身体测量（体重、身高、BMI、体脂率、去脂体重、腰围）、活动（步数、步行跑步/骑行/游泳距离、爬楼、锻炼分钟、站立时间、步行速度、活动/静息能量、体能训练）、睡眠分期、饮水与营养、正念、头痛、月经。**不接：** 运动路线（定位）、听力图、性别/生日/血型等基础资料（档案已有）、胰岛素等。月经、心电图、血糖属敏感类别；心电图只取分类结果和平均心率，不取波形。
- **汇总后再发：** 高频数据（心率等）超过 60 个点时均分成 48 段给平均/最低/最高；累计量按天合计，iPhone 与手表重复记录时每天只取合计最大的一个来源；步数用 HealthKit 统计查询；睡眠按间隔 3 小时分段，每段只取分期最多的来源，给入睡、醒来、各阶段分钟数；体能训练给起止时间，提示模型据此再读心率。
- **不入库、调用记录只写读了什么：** 读到的数据只在本次请求的内存里经过，不写健康表。调用记录的 request_text 里这部分替换为"（实时健康数据，未保存）心率 10-26 18:00~18:30（214 个点）"这类说明，问题下方同样列出。实时数据上可查的是读了什么，不是读到的数值。咨询历史只存问答文字，下一问不会带上上一问读到的数据。
- **何时提供：** 只在 iPhone 上（Mac 没有 HealthKit，仍用已同步的 `get_device_data`），且设置里开了健康数据同步。
- **授权：** 实时读取的类型与入库的四类一起申请，由启动时的 autoSync 申请：已决定的类型不再弹框，新增的类型弹一次系统授权页。iOS 不告诉应用读取是否被拒，读不到时工具返回"没有读到记录（可能没戴设备或未授权）"。

## D-45 咨询页按本机数据给示例问题

第一次进咨询页的用户不知道可以拿自己的健康和运动数据提问。不照搬 AI 对话应用的"能力标签"（那是切换工具，咨询里模型自己决定查什么），而是按本机已有数据生成可直接问的具体问题。

- **两层：** 输入框上方一排类别标签（横向滑动），点开展开 2–3 个具体问题；点问题**填进输入框，不直接发送**，可改了再发。
- **类别与出现条件（只在本地查库，不调模型）：** 睡眠（近 7 天有设备睡眠或睡眠记录）、运动（近 7 天有体能训练或运动记录；能实时读取时问"X月X日骑行时心率怎么样"，否则问强度）、心率血氧（仅能实时读取时，D-44）、检验指标（有已核对结果；最近一次异常的项目问注意事项和变化，未核对的不出题）、报告（有已核对的文字结论）、身体状况（已确认未痊愈的长期状况，问饮食和复查）、日常记录（近 7 天有饮食或心情记录）。没数据的类别不出现；什么数据都没有时只给"常见问题"。问题里的日期、项目名、状况名来自本地数据。
- **与"允许模型查阅"联动：** 关掉时需要查数据的问题置灰并提示打开；身体状况本来就在基础上下文里，不受影响。
- **显示时机：** 新对话时展开；发出第一问后收起，输入框左侧灯泡按钮可再打开。空白页说明压缩为三行。

## D-46 长期状况档案按身体系统分组，同义写法合并，疑似重复由用户确认

档案条目多了以后需要分类分组显示并合并重复项。D-32 的"同一问题"规则能合并大部分（肾结石/肾结石（多发）、双肾/左肾囊肿等），剩下两类：同义写法（"过敏性结膜炎［变应性结膜炎］"与"变应性结膜炎"、"慢性浅表性胃窦炎"与"慢性非萎缩性胃窦炎"），以及规则不该自己判断的（"肠炎"与"慢性结肠炎"、"失眠"与"失眠心脾两虚"、"咳嗽"与"风寒咳嗽证"）。

- **同义写法自动合并（`SameItem.core`）：** 方括号［］【】[] 里的别名注释和问号去掉；"过敏性"按"变应性"、"浅表性"按"非萎缩性"（慢性浅表性胃炎是旧称）。规则改了下次打开就按新规则算，人体图、咨询上下文、周报共用。
- **疑似重复由用户确认（`SameItem.maybeSameProblem`）：** 一个的核心完整出现在另一个里（≥2 字），且同一节（长期/临时）、同一系统。档案页顶部提示"有 N 组可能是同一问题"，逐对选"合并"或"不是"；"不是"记在本机设置 `condition_merge_dismissed`，不再提示。条目菜单里也可以手动"与其他条目合并…"、"取消合并"。
- **合并写进记录：** 被合并组的每条写一个新版本，data 里加 `group_name`（合并到的组名），核对状态不变，走变更日志同步到 Mac；原记录、原写法、原件定位都保留，取消合并即去掉该字段。分组时两条的分组名或原名任一是同一问题就归一组，所以以后报告里再出现被合并的旧写法也会自动归进来。合并后一行显示最新那份报告的写法。只在手机上操作（Mac 只读，D-12）。
- **按身体系统分组（`conditionCategory`）：** 心血管、呼吸、消化、泌尿生殖与乳腺、内分泌与代谢、骨骼肌肉、皮肤、眼耳鼻喉口腔、神经与精神、过敏与免疫、感染、其他。先看血压（人体图放在血液与代谢，这里归心血管），再用人体图的器官规则（D-31）映射到系统，认不出再看骨骼肌肉、皮肤、代谢等补充词。只看名称，不写库。
- **页面结构：** 长期状况（未痊愈，参与分析）按系统分组展开；既往病史（已痊愈的长期状况）与临时疾病各收成一节，默认折叠（临时疾病里有未痊愈的才展开）；各节内按系统、组内按最新报告日期。

## D-47 饮食记录有"饮水"餐次，没说哪一顿的不显示"未知"

单独喝水喝茶会被整理成 meal；如果 meal_slot 只有早/午/晚/加餐/unknown，模型只能填 unknown，按日视图里就显示成"未知：红茶"。

- **meal_slot 有 `drink`（饮水）：** 整理提示词写明单独喝水、茶、咖啡、饮料（不是随某一顿吃的）用 drink，吃了东西但说不清哪一顿才用 unknown。drink 不算三餐，每日回顾的缺口检测不受影响。
- **显示：** unknown 叫"未注明"；列表摘要里没说哪一顿的不加前缀，只显示内容。
- **存量修复（`repairDrinkSlots`，启动时跑，幂等）：** 餐次不是标准值、且模型写的是"饮水"之类，或吃的东西全是饮品（水、茶、咖啡、饮料、果汁、豆浆、牛奶等）的，归回 drink；用户核对过餐次的不动；写新版本，旧版本保留。

## D-48 对话页不提供添加照片和文件

对话里发的照片和文件不会被处理：附件只存档；整理只发文本和 attachment_count，图片不发给模型（D-24），只把相邻文字描述的饮食记录挂上照片 ID；纯图片消息会一直"待整理"；对话里发的检查单不会提取。所以对话页不提供这个入口。

- **不提供：** 对话页没有加号、拍照/选照片/导入文件及相应的重复提示。照片和 PDF 只从病例夹/体检入口添加（D-27，仍写入消息流、走 D-10 去重）。
- **保留：** 已有的附件消息照常显示、可打开；附件仓库、导出恢复、同步、整理时把照片消息关联到饮食记录的逻辑都保留（病例夹导入仍会产生附件消息）。
